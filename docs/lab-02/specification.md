# Lab 2 Sprint Engineering Specification — TokTickIT

## 1. Sprint Goal
Deliver a Requester-facing IT ticketing MVP: a Requester can create a support
ticket, track it in My Tickets, inspect it in Ticket Detail, and manage its
attachments — all under a temporary Development Requester identity that
stands in for real login until Lab 3.

## 2. Stakeholder Request Interpretation
IT is ready to accept real support tickets from end users. We need a
professional, responsive Requester experience that lets someone describe a
problem, classify it (category, related system, priority), attach evidence,
and submit it, then find that ticket again later, filter/search their own
history, open it for detail, and add or soft-remove attachments. The system
must generate the official ticket number, keep each Requester's tickets
private from other Requesters, and — because there is no real login yet —
offer a temporary "Development Requester" switcher so we can test
multi-user ownership before Lab 3 adds authentication. All screens should
share one consistent visual language (Zen Green) and reusable UI states
(loading/empty/error/validation) so later labs can build on them.

## 3. Scope

### Included
- Development Requester Selection (test-only identity switch)
- Create Ticket (category, related system, priority, summary, description, attachments)
- My Tickets (search, filter, sort, pagination)
- Requester Ticket Detail (read-only ticket info + attachments)
- Attachment lifecycle: add to existing ticket, soft-remove with reason
- Ownership protection (a Requester can never see another Requester's data)
- Zen Green shared UI conventions (forms, lists, badges, validation, loading/empty/error states, responsive layout)

### Excluded
- Real authentication (login, logout, passwords, sessions, tokens, role-based authorization)
- IT Staff dashboard/queue, claiming/reassigning tickets, changing IT Priority
- Public Comments, Internal Notes, Actions Taken
- Ticket lifecycle beyond initial "New" status (resolve, close, reopen, cancel)
- Administration functions (managing users, roles, reference data)

## 4. Functional Requirements
- **FR-01** The system shall present a Development Requester Selection screen and require a Requester to be selected before any ticket screens are accessible.
- **FR-02** The system shall persist the selected Requester as the active testing identity across navigation until changed via "Change Requester."
- **FR-03** The system shall let the active Requester create a ticket with category, related system, requested priority, summary, description, and optional attachments.
- **FR-04** The system shall generate a unique, backend-assigned Ticket Number upon successful ticket creation.
- **FR-05** The system shall let the active Requester view a paginated list of only their own tickets (My Tickets).
- **FR-06** The system shall let the active Requester search, filter, and sort their ticket list.
- **FR-07** The system shall let the active Requester open a Ticket Detail screen for any ticket they own.
- **FR-08** The Ticket Detail screen shall display current ticket information as read-only and list its attachments.
- **FR-09** The system shall let the active Requester add a permitted attachment to a ticket they own.
- **FR-10** The system shall let the active Requester soft-remove an attachment they own, with a required reason.
- **FR-11** The system shall reject any attempt to view or modify a ticket or attachment not owned by the active Requester.
- **FR-12** The system shall load Categories, Related Systems, and active Development Requesters from PostgreSQL.

## 5. Business Rules
- **BR-01** The official Ticket Number is generated by the backend and must be unique.
- **BR-02** A new Ticket begins with Current Status `New`.
- **BR-03** The Development Requester selector is a Lab 2 testing mechanism only and is not authentication.
- **BR-04** Only active Development Requesters appear in the selector; inactive Requesters are excluded and cannot be selected.
- **BR-05** Changing the selected Requester reloads all requester-scoped data (My Tickets, Ticket Detail access) for the new identity.
- **BR-06** A Ticket belongs to exactly one Requester at creation and cannot be reassigned in Lab 2.
- **BR-07** Any list/detail/attachment endpoint scopes results to the selected `requesterId`; requesting another Requester's ticket or attachment returns a not-found response rather than revealing that it exists.
- **BR-08** Ticket Summary is required, trimmed, 5–120 characters.
- **BR-09** Ticket Description is required, trimmed, 10–2000 characters.
- **BR-10** Category and Related System are required and must reference an active reference-data row.
- **BR-11** Requested Priority is required and must be one of `LOW`, `MEDIUM`, `HIGH`.
- **BR-12** The Submit control is disabled and shows a busy state while a create request is in flight, preventing duplicate submissions.
- **BR-13** On validation failure, all entered field values are preserved; only the offending fields show errors.
- **BR-14** On an API/network failure during creation, no partial Ticket is persisted and entered field values are preserved for retry.
- **BR-15** Allowed attachment types are JPG, JPEG, PNG, WEBP, and PDF only.
- **BR-16** Maximum attachment size is 5 MB per file.
- **BR-17** A Ticket may have at most five active (non-removed) attachments.
- **BR-18** Attachment removal is a soft delete (`isRemoved`, `removedAt`, `removedReason`); files are never hard-deleted.
- **BR-19** A removed attachment remains visible as metadata but cannot be downloaded or previewed, and is visually marked "Removed."
- **BR-20** Removing an attachment requires an explicit confirmation and a non-empty reason.
- **BR-21** If a Ticket is created successfully but one or more attachment uploads fail, the Ticket remains valid; each failed file is reported individually and can be retried without re-submitting the Ticket.
- **BR-22** My Tickets defaults to sorting by Created Date descending; Ticket Number, Created Date, and Last Updated are sortable.
- **BR-23** My Tickets defaults to a page size of 10 (max 50); invalid page or page-size query values fall back to the default rather than erroring.
- **BR-24** An "empty" state (Requester has zero tickets ever) is shown differently from a "no results" state (filters/search match zero of the Requester's tickets).
- **BR-25** An inactive Requester is never offered in the selector and therefore cannot become the active testing identity in Lab 2.
- **BR-26** All Development Requester identity is temporary test scaffolding; Lab 3 will replace it with real authenticated accounts, and existing `requesterId` associations are expected to carry forward unchanged.

## 6. UI Specification Summary
See `docs/lab-02/ui-spec.md` for the full Zen Green token set, component states,
and responsive rules. Summary:
- App shell: TokTickIT header (Primary green `#006B3C`), My Tickets / Create Ticket nav, active-Requester display with "Change Requester," active-page indication, responsive mobile nav.
- Development Requester Selection: dropdown of active Requesters, loading/empty/API-failure states, "for testing only" notice, keyboard-accessible.
- Create Ticket: system-generated/read-only fields visually distinct from editable fields, required-field asterisks, inline validation messages, busy Submit state, success state showing the generated Ticket Number.
- My Tickets: search box, Category/Requested-Priority/IT-Priority/Current-Status filters, sortable columns, pagination, Create Ticket action, loading/empty/no-results/failure states, responsive table→card behavior on mobile.
- Ticket Detail: read-only ticket fields grouped separately from Attachments; attachment list with add/download/remove actions and a distinct "Removed" state.
- Badges: consistent color/label treatment for Requested Priority, IT Priority, and Current Status, never relying on color alone.

## 7. Data Changes
New Prisma models (see `prisma/schema.prisma`):
- **DevelopmentRequester** — `id`, `name`, `email`, `isActive`, `createdAt`.
- **Category** — `id`, `name` (unique), `isActive`.
- **RelatedSystem** — `id`, `name` (unique), `isActive`.
- **Ticket** — `id`, `ticketNumber` (unique, backend-generated), `requesterId` (FK → DevelopmentRequester), `categoryId` (FK → Category), `relatedSystemId` (FK → RelatedSystem), `summary`, `description`, `requestedPriority` (enum), `itPriority` (enum, defaulted), `currentStatus` (enum, default `NEW`), `createdAt`, `updatedAt`.
- **Attachment** — `id`, `ticketId` (FK → Ticket), `fileName`, `storedFileName`, `mimeType`, `sizeBytes`, `isRemoved` (default false), `removedAt`, `removedReason`, `createdAt`.

Indexes: unique on `Ticket.ticketNumber`; index on `Ticket.requesterId` (ownership filtering); index on `Ticket.createdAt` (default sort); index on `Attachment.ticketId`. `Category.name` and `RelatedSystem.name` are unique to keep seeding idempotent.

## 8. API Contract
See `docs/lab-02/api-spec.md` for full request/response shapes. Endpoint summary:
- `GET /api/requesters` — active Development Requesters
- `GET /api/categories` — active Categories
- `GET /api/related-systems` — active Related Systems
- `POST /api/tickets` — create a Ticket for the selected Requester
- `GET /api/tickets` — paginated, searchable, filterable, sortable list scoped to the selected Requester
- `GET /api/tickets/:id` — one owned Ticket
- `POST /api/tickets/:id/attachments` — upload an Attachment
- `GET /api/tickets/:id/attachments` — Attachment metadata for a Ticket
- `GET /api/attachments/:id/download` — download an active Attachment
- `PATCH /api/attachments/:id/remove` — soft-remove an Attachment

## 9. Acceptance Criteria
- **AC-01** Given valid Ticket data, when the Requester submits Create Ticket, then one Ticket is saved and the official Ticket Number is displayed.
- **AC-02** Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- **AC-03** Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned.
- **AC-04** Given a required field is left blank, when the Requester submits Create Ticket, then a field-level validation message appears and no request is sent.
- **AC-05** Given a Create Ticket request is in flight, when the Requester clicks Submit again, then the button is disabled and no duplicate Ticket is created.
- **AC-06** Given the create-ticket API call fails, when the failure occurs, then a safe error message is shown and all entered field values remain in the form.
- **AC-07** Given a Requester selects a 6 MB file, when they attempt to attach it, then the file is rejected with a clear size-limit message and no upload request is sent.
- **AC-08** Given a Ticket already has five active attachments, when the Requester attempts to add a sixth, then the addition is blocked with an explanatory message.
- **AC-09** Given an active attachment, when the Requester removes it with a reason, then it is marked removed, remains listed as metadata, and can no longer be downloaded or previewed.
- **AC-10** Given My Tickets has tickets from the active Requester only, when the screen loads, then only that Requester's tickets appear, sorted by Created Date descending by default.
- **AC-11** Given a search term that matches no ticket, when the Requester searches, then a distinct "no results" state is shown (not the empty-history state).
- **AC-12** Given a Requester with zero tickets ever created, when My Tickets loads, then the empty-history state is shown with a Create Ticket call to action.
- **AC-13** Given the active Requester is changed via "Change Requester," when the switch completes, then My Tickets reloads to show only the newly selected Requester's tickets.
- **AC-14** Given the reference-data API (Categories/Related Systems/Requesters) fails to load, when Create Ticket or the Requester Selector opens, then a safe failure state is shown instead of a blank or broken form.
- **AC-15** Given the viewport is narrower than 768px, when any Lab 2 screen is viewed, then fields stack vertically, buttons remain touch-friendly, and no horizontal scrolling occurs.

## 11. Assumptions and Decisions
- Requested Priority values are `LOW` / `MEDIUM` / `HIGH`; IT Priority uses the same enum but defaults to `MEDIUM` and is not editable by the Requester in Lab 2 (IT Staff workflow is out of scope).
- Ownership violations return a not-found response rather than a forbidden response, to avoid confirming another Requester's ticket exists.
- Ticket Number format: `TKT-{year}-{zero-padded sequence}` (e.g. `TKT-2026-000123`), generated transactionally on the backend to guarantee uniqueness.
- Attachment storage uses a randomized `storedFileName` on disk/storage while retaining the original `fileName` for display, to avoid collisions and path-traversal risk.
